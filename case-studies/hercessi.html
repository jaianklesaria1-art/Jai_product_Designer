01Executive summary

A balanced audit, then a second look

Accord BioPharma is a client of Asentech, where I work. I picked one of their live sites and set myself a real task. In September I found ten issues across two pages, and seven checks that passed. Two months later I went back to see what still held. One finding was fixed, three improved, and one new problem now blocks keyboard users completely.

02Scope and method

Measured, not eyeballed

Two pages: the homepage and the Patient Support registration page. Six checks, in this order.

  1. Task completion

    One real goal, place an order, attempted exactly as a visitor would: mouse first, then keyboard only, with the console open.

  2. Keyboard-only pass

    Real Tab presses from a fresh page load, logging which element took focus each time.

  3. Disclosure check

    For each dropdown, compared the submenu's computed display before and after keyboard focus reached its trigger.

  4. Computed style

    Read getComputedStyle on the focused element after each Tab, so a missing focus ring is a measured fact.

  5. DOM queries

    Counted images without alt, mapped the heading sequence, and checked every field for a linked label.

  6. Contrast and size

    Contrast from computed RGB with the WCAG luminance formula; targets measured with getBoundingClientRect.

One boundary held throughout: I never submitted the real Patient Support form. That would push fake data into a live business system that isn't mine to test that way.

04Key findings

The three that matter most

F-11New, criticalWCAG 2.1.1 Keyboard, A

Every Tab keypress is cancelled

I first noticed it on 22 September, when I couldn't tab into the nav. On 18 November I logged it properly. On both pages, every Tab keydown arrives with defaultPrevented already true. The browser never moves focus. The cookie banner is hidden, so it isn't the cause. Which script does it, I haven't isolated.

To rule out my own tooling, I ran the same five Tab presses on GOV.UK. Focus moved normally: skip link, logo, menu, search.

RecommendationFind the keydown listener calling preventDefault on Tab (often a modal focus trap left running after the modal closes) and limit it to when that modal is open.

F-03Still failingWCAG 3.3.2 Labels or Instructions, A

The registration form has no labels

Seven fields: first name, last name, business email, ZIP, profession, organisation and request type. None has a label element, aria-label or aria-labelledby. Five rely on placeholder text, which disappears as soon as someone types. The placeholder is also the same colour as typed text (#2F2F2F), so a filled field and an empty one look alike. In November, the two dropdowns had no placeholder at all.

RecommendationAdd a visible <label for> to every field. Keep placeholders as hints only, in a lighter colour.

F-01FixedNo WCAG line item

The Order Now button that did nothing

In September every page had an Order Now link with href="#". Clicking it did nothing, and the console showed no errors. No WCAG checklist would catch it. I only found it by trying the real task. By 22 September a click opened a distributor list. The November redesign moved the button into the hero, where it links to a real Ordering Details section.

Why it stays in the case study: finding it took a task-based test, and checking it was fixed took a second visit. Both are part of the method.

06Prioritisation

What to fix first, as of November

Ordered by impact against effort, not severity alone.

Fix first

  1. Unblock Tab (F-11). Nothing else can be tested by keyboard until it's fixed, so it goes first.
  2. Add aria-expanded to the Ordering Details toggle (F-06). A few attributes.
  3. Label the safety-information toggle (F-09) and give the last image alt text (F-07).
  4. Renumber the H5s to H4 (F-10). Keep the visual size in CSS.

Fix next

  1. Add real labels to the form (F-03). A layout change: each row gets taller by the label height.
  2. Re-run the keyboard pass once Tab works, starting with the Ordering Details submenu (F-05).
  3. Check the entry gate if it comes back (F-02, F-08).

07Handoff format

Written the way I'd hand them over

Steps to reproduce, the fix, and acceptance criteria. This is the format I would use. These tickets were never filed with Accord BioPharma or Asentech.

TICKET F-11Critical

Tab key is cancelled site-wide

Steps to reproduce

  1. Load hercessihcp.com
  2. Press Tab several times
  3. See that focus never leaves the page body

Fix

Find the keydown listener that calls preventDefault on Tab and scope it to the open modal only.

Acceptance

  • Tab moves through every link and control in order
  • "Skip to content" is the first or second stop
TICKET F-03High

Registration form fields have no labels

Steps to reproduce

  1. Open Patient Support
  2. Inspect any field
  3. See no label, aria-label or aria-labelledby

Fix

Add a visible <label for="id"> to all 7 fields. Lighten the placeholder colour.

Acceptance

  • Every field has a label you can see before and while typing
  • Each label is linked via for/id
TICKET F-01Closed, Nov

Order Now has no destination

Steps to reproduce (Sept)

  1. Open any page
  2. Activate Order Now
  3. Nothing happens, no error

Fix

Point it at the real ordering flow.

Verified 18 Nov

  • Links to an Ordering Details section on the page
  • Keyboard check blocked by F-11

08Conformance notes

Listed so this reads as a balanced assessment. Rows marked Nov were measured on 18 November; the rest are from September.

  • 3.1.1<html lang="en-US"> set site-wide. Still true in Nov.
  • 1.3.1All four landmarks present: main, nav, header, footer. Still true in Nov.
  • 2.4.2Page titles are descriptive and unique. Still true in Nov.
  • 1.4.3Submit button text 8.81:1 (Nov). Gate button text was 8.81:1 in Sept.
  • 1.4.11Field border #F36C23 on white measures 3.01:1 (Nov). Just over the 3:1 minimum.
  • 2.5.8Submit button 154 × 54 px (Nov). Gate buttons were 93 × 29 px in Sept. Both clear 24 × 24.
  • 1.4.3Boxed warning and nav text both measured 13.39:1 in Sept.

What a checklist would have missed

A criterion-by-criterion pass catches F-02 and F-03. It doesn't catch a main button that does nothing, and it doesn't catch a fix that breaks the keyboard two months later. Doing the real task, and coming back to do it again, caught both.

Being honest about change

A live site is a moving target. The September findings stay in the report as I recorded them, and each one is dated. Where the site has changed, the re-check says so, including the fixes.
